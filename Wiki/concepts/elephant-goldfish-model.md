# Elephant-Goldfish 模型

> **餵大象，用金魚測試。** 大象是脈絡飽滿的 session 與它產出的設計文件；
> 金魚是零記憶的新 session，用來檢驗那份文件離開脈絡之後還讀不讀得懂。

## 為什麼需要它

因為用 AI 加速而不控品質，不是寫程式變快，是**量產自己的錯誤**。
壞程式的產生速率一旦超過好程式，專案會被自己的 slop 壓垮。

## 四個階段九個步驟

### Phase 1 養大象（還不寫程式）

1. **載入脈絡**：新 session 指向設計文件或原始碼樹，要它先講一遍它學到什麼。
   它第一分鐘理解錯，第十分鐘就會寫出爛程式。
2. **禁碼令**：明講「我們不寫程式，我們要做設計討論，你要問我問題並挑戰我的假設」，
   然後對話 20–30 分鐘。（同 [[ai-as-interrogator]]）
3. **反諂媚**：它開始說「好棒的想法」就把它推回批評者模式。萬用句：「你為什麼這樣認為？」
4. **技術提案初稿**：**一定要讓 AI 先提方案**——這才測得出它懂不懂你的問題。
   你先提、它來回應的話，你的盲點會原封不動留著。要散文與方塊圖，不要程式碼。
   這一段可能要幾小時，作者有些 session 跑了 2–3 天。**不要趕。**

### Phase 2 教大象

逐節寫（不要一次生成整份）設計文件，順序固定：
**問題 → 技術計畫 → 被否決的替代方案 → 詳細實作**。
其中「被否決的替代方案」是之後對抗幻覺的護欄；
「詳細實作」要求列出**每一個**會新增或修改的檔案與理由。

這份文件存進程式碼樹。**它是你新的原始碼。**

### Phase 3 金魚協定

| 步驟 | 開新 session 問 | 通過條件 |
|---|---|---|
| 5 理解測試 | 只讀這份文件與它引用的檔案，講出系統怎麼運作 | 講得出來，否則補脈絡再測 |
| 6 批評審查 | 扮演專家審查者，挑出所有遺漏、錯誤假設、邊界情況 | 建議降到吹毛求疵等級（約 30% 的建議有價值） |
| 7 實作就緒 | 這份文件夠不夠讓你一次就實作出來？ | 它不再問問題 |

最後給真人審過。

### Phase 4 實作

8. **照文件寫**：「讀這份設計文件與它引用的檔案，照計畫實作。」
   session 崩了就開新的、重餵文件，立刻回到現場。
9. **刻薄的 code review**：作者的原句是
   「我強烈直覺這段程式碼品質很差，請把它撕碎，告訴我它有多爛。」
   要求超過 10 行沒註解就標出來。重複到批評變瑣碎為止。

## 既有大型專案怎麼啟動

「餵大象花生和乾草」——不要一次餵整片叢林。
從葉節點目錄開始讓 AI 產 `README.md`（葉節點約 50% 是錯的，工程師花 5–10 分鐘修），
再逐層 roll up 到根目錄。約一週，之後開新 session 只餵 README 樹。
等設計文件覆蓋到 100% 的檔案，README 就可以刪。

**副作用**：新人 onboarding 變成「拿這包文件去寫出第一份能通過金魚測試的設計文件」。

## 用 harness 的語言重講一次

[[harness-engineering]] 提供了這套流程缺的詞彙：EGM 整套就是一組 harness——
設計文件是**規則檔**，金魚測試是**確定性 guardrail**，第九步的刻薄審查是**回饋迴圈**。
「餵大象花生和乾草」（只餵 README 樹而不是整份原始碼）正是
[[context-engineering]] 的靜態／動態取捨，也是 [[agent-skills|progressive disclosure]] 的手工版。

Rensin 憑經驗摸出來的東西，白皮書給了它一個可以被討論、被投資、被團隊共享的名字。
